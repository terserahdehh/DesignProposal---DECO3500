The hardware contains no GPS or magnetometer. A laptop location represents that laptop; giving both bands the same laptop position cannot locate two separately moving people. Each wearer should use their own Android Chrome phone, connect their own band and select **Keep location updated**. A reported north-up arrow needs a compass for orientation. Poor/overlapping GPS accuracy suppresses the bearing. Vercel hosts the frontend; it supplies neither GPS coordinates nor a radio relay.

Web Bluetooth requires a secure context and a supported browser, as described in [Chrome's Bluetooth documentation](https://developer.chrome.com/docs/capabilities/bluetooth). Modern Chrome may also request [Local Network Access](https://developer.chrome.com/blog/local-network-access) for the USB bridge. Ordinary iPhone browsers do not support the Direct Bluetooth flow. A plain HTTP page at a laptop LAN address usually cannot request browser location; use HTTPS or localhost.

## Issues reproduced and fixed test-first

- Bluetooth complete status updates could retain a previous bearing after firmware omitted expired guidance. Merge logic now removes it.
- `/phone` ignored unsolicited `message`, `sent`, `send_failed` and `dismissed` Bluetooth events. Custom messages now update the physical band state immediately.
- USB snapshots discarded the device sequence for repeated messages. They now retain it so the browser can show the next popup even when text repeats.
- Browser transports accepted old/future/fractional location timestamps. Shared validation rejects them; queued Bluetooth writes revalidate before transmission.
- Continuous browser location watching remained active after a band disconnect. The page clears the watch and rejects late callbacks.
- A contradictory top-level/nested owner in a Bluetooth hello could enable configuration. Handshake now rejects conflicting identities.
- The deployed `/phone` endpoint returned HTTP 404 because its rewrite destination was `/index.html` while `cleanUrls:true` removes HTML extensions before routing. It now rewrites to `/`, which serves the root export without changing the browser path. A deployment configuration regression test and the UI test server enforce this behavior. See [Vercel's clean URL rules](https://vercel.com/docs/project-configuration/vercel-json#cleanurls).

The `/phone` live status card and incoming popup are added with expiry, peer availability and reported quality checks. A browser popup can be hidden independently of the physical watch's unread state. Public HTTPS pages start with Direct Bluetooth; localhost starts with USB.

## Physical follow-up after both USB bands were connected

Both owner/MAC pairs were verified, built successfully with PlatformIO and flashed over the verified USB ports. The pre-update firmware range `0x000000–0x30ffff` and saved presets were backed up locally per band in `hardware/backups/2026-10-12-*-before-arc.*`. The old local pairing-key source was unavailable, so both matching builds now use the same newly generated, ignored key. Keep `hardware/include/pairing_keys.h` to rebuild either band. Source builds do not include this key in GitHub or Vercel.

The [physical arc verifier](verify_direction_arc.py) passed seven checks. Actual framebuffer pixels confirmed Nayaka's yellow arc and Syifa's purple arc cover one quarter only, follow east/west then north/south bearings, and become brighter when known separation decreases from about 111 m to 11 m. Uncertain and cleared positions suppress both arcs. This uses explicitly labelled demo coordinates rather than real phone GPS; both bands restored their original five presets and cleared test positions.

The display verifier passed **26 checks with 24 real atomic framebuffer captures**: homes, empty-message menus, 40-character messages/confirmations/popups in both directions, sender indicators, acknowledged results, three SOS states and unavailable/usable/uncertain direction. Generated watch pixels stay within the round display. Results are in the ignored `hardware/artifacts/display-arc-live-2026-10-12.json` and `display-review.png`.

The [live browser verifier](verify_phone_usb.py) passed against both the local production export and **https://pulseband-steel.vercel.app/phone** in Chrome 154, using real USB serial and ESP-NOW rather than doubles. Both owners, correct-colour direction previews, load/add/edit/delete/manual sync with independent firmware readback, repeated physical/browser popups, peer acknowledgements, position clearing, mobile layout and absence of uncaught browser errors were verified. Original presets were restored and demonstration fixes cleared.

Timed expiry testing exposed an unwanted touchscreen action while the user confirmed both watches were untouched. Raw Down/Contact reports could previously invoke a button. The touch filter now acts only on a completed SingleClick release, de-duplicates it, and includes the gesture interrupt. Native regression tests cover noise, lone contact, held fingers, duplicate reports and separate confirmations. Firmware touch counters now support a hands-off test. Gesture and IRQ configuration follow the [CST816S register description](https://files.waveshare.com/wiki/common/CST816S_register_declaration.pdf).

After the touch fix was flashed on both watches, the full **13-check USB/ESP-NOW pair run passed**, including an actual restart, saved presets, bidirectional acknowledged messages, sender-colour popups/dismissal, SOS cancellation and three-confirmation delivery, known-position direction, overlapping/coincident suppression and restoration, and the real 60-second expiry. With `--quiet-touch`, both touchscreen action counts stayed unchanged and no screen interruption occurred. Both arrows and quarter arcs disappeared after expiry while the ESP-NOW peer connection remained active. Original presets were restored; demo positions cleared. Report: ignored `hardware/artifacts/pair-arc-quiet-live-2026-10-12.json`.

Both boards also stored and read back eight 40-character messages with 32-character IDs and escaped quotes/backslashes. Nine messages, 41-character text and emoji were rejected by the firmware without replacing the saved list. Both original preset lists matched the pre-flash backup exactly afterward. The actual browser checks were rerun on localhost and Vercel after the touch fix and passed with the physical bands again.

An opt-in finger-tap monitoring window saw no touch reports or actions on either device; no successful human tap was supplied during that window. This quiet result does not validate physical finger response. The controller-confirmed gesture path has native regression coverage, but user-performed finger taps and actual two-phone GPS/Bluetooth should be confirmed on the physical setup. No claim is made that indoor positioning or wrist-relative compass tracking is supported.
